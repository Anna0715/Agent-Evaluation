## Context
周报追问 Agent 评测对象是「对已授权周报做追问」，不是从零生成周报。现网执行器用 `chat/report/stream` 只覆盖文本追问；图片、点赞、记忆、权限变更等需要独立环境。参考 Agent 评测七层框架：先定义任务与成功标准，再分层数据集，规则能判则规则判，环境缺失显式 skip，失败回流数据集。

## Goals / Non-Goals
- Goals:
  - 把成功标准从「关键词覆盖率」改为「合同 + 红线 + 质量分」。
  - 未执行的环境类用例记待复测，降低虚假失败率。
  - 离线重打分可复现，人工改判可回写。
- Non-Goals:
  - 首期不引入真实 LLM Judge 作为默认打分器。
  - 不在本次补齐图片/点赞/记忆的真实环境（只正确标记缺口）。
  - 不改变周报生成生产逻辑。

## Decisions
- Decision: 质量分与门禁分离。加权分只描述质量；通过/失败由 critical 红线和合同决定；完整度不足最多落到人工复核，不能单独变红线。
- Decision: 环境缺口 = skip/待复测，不算失败也不算通过。
- Decision: 红线仅限真实安全/状态造假。源材料中的「越权」叙事、输出中的历史复盘、50人×12周算术，一律不是 SEC 红线。
- Decision: 打分器版本写入每条结果（`scorer_version`），数据集版本与执行记录一并归档。
- Alternatives considered: 继续调高通过阈值或调低完整度权重。这会掩盖错误的成功标准，不采用。

## Risks / Trade-offs
- 待复测变多可能被误认为覆盖下降 → 报告必须单列待复测与原因。
- 通过率上升可能被质疑放水 → 同时给出合同失败清单和红线清单，门禁用 critical 而非均分。

## Migration Plan
1. 落地 `eval_engine` 并用历史执行记录离线重打分。
2. 新跑次默认走新引擎。
3. 人工复核台继续写「人工复核」列，作为飞轮输入。
